# ADR-011: PostgreSQL Roles and Extensions

- **Status:** Accepted
- **Date:** 2026-11-17
- **Amended by:** [ADR-012](0012-single-organization-deployment.md) — tenant isolation упразднена; RLS, если будет
  введена, служит вторым рубежом для доступа на уровне KB, а не для изоляции организаций.

## Context

Схема требует расширений `vector` (pgvector) и `citext` ([DATABASE_SCHEMA.md §9](../DATABASE_SCHEMA.md)). Первая
версия каркаса выполняла `CREATE EXTENSION` в ревизии Alembic `0001`. Это работало только потому, что dev-compose
подключал и миграции, и API под суперпользователем PostgreSQL (`POSTGRES_USER` образа).

Владелец проекта не допускает постоянных прав суперпользователя у приложения или у роли миграций в production.
Компрометация API (SQL injection, RCE в зависимостях, утечка `DATABASE_URL`) не должна давать чтение файлов сервера,
`COPY ... PROGRAM`, создание untrusted-языков и обход Row Level Security, которую планируется добавить как второй
рубеж tenant isolation ([SECURITY_MODEL.md §5](../SECURITY_MODEL.md)).

Установка расширения — действие уровня администратора БД. Это не изменение схемы приложения. Во многих управляемых
PostgreSQL (RDS, Cloud SQL, Azure) у клиента вообще нет суперпользователя, а расширения включаются отдельной
процедурой провайдера.

## Decision

1. **Расширения устанавливает администратор БД, а не миграции.** Список и команды — в файле
   `deploy/postgres/extensions.sql` (идемпотентный, `CREATE EXTENSION IF NOT EXISTS`). Его выполняют один раз на БД
   ролью с правом создавать расширения, **до** первого `alembic upgrade`.
2. **Миграции только проверяют наличие расширений.** Ревизия `0001` читает `pg_extension` и при отсутствии
   расширений завершается ошибкой. Ошибка перечисляет недостающие расширения и указывает на
   `deploy/postgres/extensions.sql`. Миграции не выполняют `CREATE EXTENSION` и `DROP EXTENSION`. `downgrade`
   расширения не удаляет.
3. **Роли.**
   - **Привилегированная роль** (суперпользователь или роль администратора управляемого PostgreSQL) используется
     только администратором для установки: создание ролей, БД, расширений, обновление версий расширений. Её учётные
     данные не передаются ни одному сервису приложения.
   - **Роль приложения** — `LOGIN NOSUPERUSER NOCREATEROLE NOREPLICATION NOBYPASSRLS`. Она владеет базой
     приложения (может создавать таблицы, индексы, типы в своей БД). Под ней работают миграции (`migrate`) и
     сервисы (`api`, позднее worker).
4. **Новые расширения** (например, для FTS) добавляются через изменение `extensions.sql`, проверку в новой ревизии
   и инструкцию по обновлению в release notes. `ALTER EXTENSION … UPDATE` — тоже задача администратора.
5. **Среда разработки** воспроизводит ту же модель. Суперпользователь `postgres` образа используется только
   init-скриптом `deploy/postgres/initdb/10-dev-roles-and-extensions.sh` (выполняется при создании volume). Скрипт
   создаёт роль приложения и её БД и устанавливает расширения в эту БД и в `template1`. Только в разработке роль
   приложения получает `CREATEDB`: integration-тесты создают временные БД.
6. Integration-тесты закрепляют модель: роль приложения не является суперпользователем; миграция на БД без
   расширений падает с понятной ошибкой и ничего не создаёт; downgrade не удаляет расширения.

**Отложено.** Разделение роли миграций (владелец схемы) и runtime-роли API/worker (только DML, без DDL) —
отдельным решением не позже введения RLS (Фаза 2 / 12). Тогда же — `REVOKE CREATE ON SCHEMA public FROM PUBLIC` и
явные `GRANT` для runtime-роли.

## Alternatives

| Вариант | Почему не выбран |
|---|---|
| Приложение и миграции под суперпользователем | Отклонено владельцем: компрометация API = полный контроль над СУБД и файлами сервера |
| `CREATE EXTENSION` в миграции под владельцем БД (PostgreSQL 13+ trusted extensions) | `vector` и `citext` сейчас помечены `trusted`, но это свойство пакета расширения и политики провайдера, а не гарантия. Управляемые БД часто требуют отдельной процедуры (allowlist расширений, особая роль). Поведение миграции зависело бы от окружения |
| Отдельная привилегированная миграция (вторая цепочка Alembic / флаг `--privileged`) | Требует передавать привилегированные учётные данные в контейнер `migrate` при каждом обновлении; усложняет pipeline ради двух строк SQL |
| Проверка расширений только в readiness | Ошибка проявлялась бы позже и менее понятно: миграции с типом `vector` падали бы на `type "vector" does not exist` |

## Consequences

- Установка на сервер получает ручной шаг до первой миграции: выполнить `deploy/postgres/extensions.sql` от
  имени администратора ([DEPLOYMENT.md §6.1](../DEPLOYMENT.md)).
- Без этого шага `migrate` завершается с ненулевым кодом и понятным сообщением, API не стартует (зависит от
  `migrate`), readiness не проходит.
- Существующие dev-volumes, созданные до этого решения (роль приложения была суперпользователем), нужно
  пересоздать: `docker compose down -v` (удаляет локальные данные разработки).
- Downgrade до `base` больше не удаляет расширения. Это намеренно: расширения принадлежат администратору, и их могут
  использовать другие объекты БД.

## Security considerations

- Принцип наименьших привилегий: у роли приложения нет `SUPERUSER`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS`;
  в production — и `CREATEDB`. Функции чтения файлов сервера (`pg_read_file`) ей недоступны (покрыто тестом).
- Учётные данные администратора не попадают в `.env` приложения, образы и логи. В dev-compose пароль `postgres`
  нужен только контейнеру `postgres` и не передаётся сервисам `migrate`/`backend`.
- `NOBYPASSRLS` сохраняет смысл будущих политик RLS для роли приложения.

## Implementation notes

- `apps/backend/alembic/versions/0001_require_extensions.py` — проверка расширений
  (`MissingExtensionsError`). В offline-режиме (`alembic upgrade --sql`) выводит комментарий с требованиями.
- `deploy/postgres/extensions.sql` — единственный список требуемых расширений вне кода. При добавлении расширения
  обновить его и `REQUIRED_EXTENSIONS` в миграции.
- `compose.yaml`: `POSTGRES_PASSWORD` — пароль суперпользователя (только контейнер `postgres`);
  `PLUMMY_DB_USER` / `PLUMMY_DB_PASSWORD` / `PLUMMY_DB_NAME` — роль и БД приложения, из них собирается
  `DATABASE_URL`.
