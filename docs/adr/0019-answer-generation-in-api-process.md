# ADR-019: Answer Generation in the API Process

- **Status:** Accepted
- **Date:** 2026-11-25 (утверждено владельцем проекта вместе с планом Фазы 8)

## Context

Фаза 8 ([DEVELOPMENT_ROADMAP.md](../DEVELOPMENT_ROADMAP.md)) добавляет ответы ассистента потоком
(`POST /api/v1/chat/stream`, SSE — [API_CONTRACTS.md §3](../API_CONTRACTS.md)). Черновик
[ARCHITECTURE.md §9.4](../ARCHITECTURE.md) предлагал генерацию в процессе API **[Proposed]**; открытыми оставались
место генерации, остановка, обрыв соединения и `Last-Event-ID` (API_CONTRACTS §3.5, §7).

Факты и ограничения:

- Генерация — ожидание сети: embedding запроса, retrieval в PostgreSQL, затем поток токенов от `LLMProvider`.
  CPU почти не тратится; длительность — секунды или десятки секунд, а не минуты.
- §11 blueprint требует выносить «долгие операции» в Celery. Ingestion — именно такая операция (парсинг, OCR,
  много документов); один ответ пользователю — нет.
- Пользователь ждёт ответ в открытом соединении; промежуточного хранилища токенов нет.
- API может работать в нескольких процессах (uvicorn workers, несколько контейнеров): запрос остановки может
  прийти не в тот процесс, где идёт генерация.
- Redis уже обязателен (rate limit, брокер Celery); при его недоступности ограничивающие endpoints отвечают `503`.
- Все исходящие вызовы провайдеров идут через `SafeHttpClient` ([ADR-007](0007-network-access-and-local-llm.md));
  ключи провайдеров расшифровываются только в процессе, который их использует
  ([ADR-016](0016-secret-encryption.md)).

## Decision

### 1. Генерация в процессе API

Use case `SendMessage` выполняется в запросе `POST /chat/stream`: авторизация (ADR-005), сохранение сообщения
пользователя, retrieval, сборка запроса, поток `LLMProvider.stream_chat`, фильтр citation IDs, сохранение ответа.
SSE-ответ — асинхронный генератор FastAPI; Celery в генерации не участвует.

### 2. Ограничения ресурсов

- **Rate limit `chat`:** 20 сообщений в минуту на пользователя (API_CONTRACTS §5) — до начала потока, `429`.
- **Не более 2 одновременных генераций на пользователя:** счётчик-семафор в Redis с TTL, равным жёсткому timeout
  плюс запас, чтобы упавший процесс не держал слот вечно. Превышение — `429 rate_limited` до начала потока.
- **Жёсткий timeout генерации:** 120 с на весь ответ (конфигурация `CHAT_GENERATION_TIMEOUT_SECONDS`, 10–600). По
  истечении — событие `error` с `code = provider_timeout`, частичный ответ сохраняется со статусом `failed`.
- Redis недоступен → `503 service_unavailable` до начала потока (генерация без лимитов не запускается).

### 3. Остановка

`POST /chat/runs/{id}/stop` проверяет владельца диалога и ставит в Redis флаг `chat:stop:{run_id}` с коротким TTL.
Процесс, ведущий генерацию, проверяет флаг между фрагментами потока и не реже раза в 0,5 с; при флаге он отменяет
поток провайдера через `CancellationToken`, сохраняет частичный ответ (`stopped`, `finish_reason =
user_cancelled`) и закрывает поток событием `message_complete`. Повторный вызов и вызов для завершённой
генерации — `202` без эффекта.

### 4. Обрыв соединения

Если клиент закрыл соединение, генерация **отменяется** (фоновое дописывание не выполняется): частичный ответ
сохраняется со статусом `stopped` и `finish_reason = user_cancelled`, `generation_runs.error_code =
client_disconnected`. Токены после обрыва не тратятся.

### 5. Без переподключения

`Last-Event-ID` в MVP не поддерживается; поле `id:` в кадрах не отправляется. После обрыва клиент перечитывает
сообщения диалога (`GET /conversations/{id}/messages`) и видит сохранённый частичный ответ.

### 6. Повтор отправки

`client_message_id` уникален в диалоге (`UNIQUE (conversation_id, client_message_id)`). Повтор с тем же ID не
создаёт новых сообщений и не запускает генерацию: `409 message_already_sent` с `user_message_id` и
`assistant_message_id`; клиент перечитывает сообщения.

## Alternatives

- **Генерация в Celery worker с ретрансляцией через Redis pub/sub.** Изоляция от процесса API и переживание
  перезапуска API, но: вторая очередь с жёсткими требованиями к задержке, ретрансляция каждого токена, сложная
  остановка и обрыв, ключи провайдеров в ещё одном процессе. Выигрыш не нужен MVP; вернуться можно отдельным ADR,
  если генерация станет тяжёлой (tools, длинные цепочки).
- **Дописывание в фоне после обрыва + `Last-Event-ID`.** Удобнее при нестабильной сети, но тратит токены на ответы,
  которые могут не понадобиться, и требует буфера событий. Отложено.
- **Отдельный сервис генерации.** Противоречит модульному монолиту ([ADR-002](0002-modular-monolith-and-layering.md)).

## Consequences

- Процесс API держит открытые соединения на время ответа; число одновременных генераций ограничено лимитом на
  пользователя и числом процессов API. Для prod-развёртывания нужен прокси без буферизации SSE
  (`X-Accel-Buffering: no`, увеличенный `proxy_read_timeout`) — Фаза 11 (Nginx).
- Перезапуск API обрывает текущие ответы: они остаются со статусом `streaming` до задачи очистки, которая переводит
  такие сообщения в `failed` (`error_code = interrupted`).
- Остановка работает при любом числе процессов API за счёт флага в Redis.
- Celery по-прежнему только для долгих операций (ingestion, purge, очистка).

## Security considerations

- Авторизация ассистента и его KB — до retrieval и до передачи текста в LLM, на **каждом** сообщении
  ([ADR-005](0005-assistant-access-model.md)); идентификаторы KB от клиента не принимаются.
- Остановка доступна только владельцу диалога; чужой или несуществующий run — `404`.
- Лимиты защищают от исчерпания ресурсов и расходов на провайдера (§8 п.5).
- Текст запроса к модели, retrieved context и ответы не пишутся в логи; в `generation_runs` — только ID chunks,
  счётчики и метрики.
- Ошибки провайдера в потоке передаются кодом (`provider_error`, `provider_timeout`, `egress_denied`), без
  внутренних деталей.

## Implementation notes

- `application/chat`: `SendMessage` (поток доменных событий), `StopGeneration`; порт `GenerationControl`
  (семафор и флаг остановки) с реализацией на Redis.
- API отображает доменные события в кадры SSE (API_CONTRACTS §3.3); heartbeat каждые 15 с без других событий.
- Задача `scheduler` переводит зависшие `streaming`-сообщения в `failed`.
