# ADR-006: Initial Setup and System Configuration

- **Status:** Accepted
- **Date:** 2026-11-17

## Context

Blueprint требует Docker Compose quick start, создание первого администратора, setup wizard и понятную диагностику
старта (§5), но в группах endpoints (§10) нет ни первоначальной настройки, ни системных настроек. Публичный setup
endpoint на свежей инсталляции — классический вектор захвата: кто первым вызовет его, тот станет администратором.
Кроме того, часть настроек (сеть, хранилище, ключи, лимиты) влияет на безопасность всей инсталляции и не должна
меняться администраторами отдельных организаций.

## Decision

### 1. Два уровня конфигурации

| | Instance Settings | Organization Settings |
|---|---|---|
| Область | Вся инсталляция | Одна организация |
| Кто управляет | Владелец инсталляции с доступом к серверу | Organization Admin (`org.settings.manage`) |
| Где задаются | Конфигурация сервера: переменные окружения, `*_FILE`-секреты, конфигурационный файл | БД, через API |
| Изменение через публичный API | **Нет.** Platform Owner видит их только на чтение (без секретов) | Да, в пределах instance policy |
| Применение | При старте процессов; изменение → перезапуск API/worker | Немедленно |
| Примеры | Network allowlist (ADR-007), конфигурация локальных LLM-endpoints, параметры внешних сервисов (OAuth client ID/secret Google и Microsoft), storage, SMTP, системные лимиты и их верхние границы, настройки безопасности (TTL сессий, CORS origins, публичный URL), параметры фоновых задач, режим setup | Название, настройки интерфейса (язык по умолчанию), организационные политики (например, срок хранения диалогов), настройки пользователей (более строгая парольная политика), параметры использования AI-функций в пределах instance policy |

**Граница:** Organization Settings могут только **сужать** то, что разрешает instance policy, и никогда не расширяют
её. Каждое значение организации валидируется против текущих Instance Settings при записи и ограничивается ими при
чтении (effective value = более строгое из двух). В Organization Settings нет полей, задающих сетевые адреса,
хранилища, ключи или системные лимиты выше instance-границ.

### 2. Хранение и типизация

- **Instance Settings** — типизированная модель Pydantic Settings; источники: env → `*_FILE` (Docker secrets) →
  конфигурационный файл для структурированных значений (allowlist). Невалидная конфигурация → отказ старта с понятной
  диагностикой (§5). Секреты — `SecretStr`, загружаются из файлов, не выводятся ни в логи, ни в API.
- **Organization Settings** — типизированная версионированная модель (`OrganizationSettingsV1`), сохраняемая в
  `organizations.settings` (`jsonb`) вместе с `settings_version`. Неизвестные поля отклоняются. Секретов в Organization
  Settings нет: секреты организации (API keys провайдеров, OAuth tokens) живут в `secret_references` (ADR-004,
  DATABASE_SCHEMA).
- **Состояние инсталляции** (`instance_state`) — единственная строка в БД с флагом инициализации и хэшем bootstrap
  token. Это не таблица настроек, а системное состояние, которое должно быть атомарным и общим для всех реплик API.
- Универсальная таблица «ключ–значение» **не создаётся**: она теряет типизацию и валидацию и позволяет смешать
  instance- и org-уровни.

### 3. Первоначальная настройка — группа `/api/v1/setup/`

- `GET /api/v1/setup/status` — публичный; возвращает только `initialized | uninitialized` и доступен ли web-setup.
- `POST /api/v1/setup/initialize` — создаёт первую организацию и первого администратора (роли Platform Owner и
  Organization Admin) и выполняет стартовые действия (системные роли и permissions уже созданы миграцией).

**Bootstrap token (защита от захвата):**

1. При установке одноразовая init-команда (`plummy setup init-token`, запускается в шаге миграций) генерирует
   случайный токен ≥ 256 бит, сохраняет в `instance_state` только его хэш и срок действия (по умолчанию 24 ч), а
   открытое значение пишет в файл на защищённом volume (`0600`). В логи попадает только путь к файлу.
2. Владелец читает токен через доступ к серверу (`docker compose exec … cat …` или `plummy setup show-token-path`)
   и вводит его в setup wizard.
3. `initialize` без валидного, неиспользованного, неистёкшего токена отклоняется. Сравнение — constant-time.
4. Альтернатива для закрытых сред: `PLUMMY_SETUP_MODE=cli_only` — web-initialize отключён полностью, первый
   администратор создаётся командой `plummy admin create`.

**Обязательные свойства:**

| # | Требование | Как обеспечено |
|---|---|---|
| 1 | Только до завершения настройки | Флаг `instance_state.initialized_at`; проверка в той же транзакции |
| 2 | Проверка на backend | Use case `InitializeInstance`; статус от frontend не учитывается |
| 3 | Атомарность | Одна транзакция: блокировка строки `instance_state` → проверки → организация, пользователь, роли → флаг → погашение токена → audit |
| 4 | Нет двух первых администраторов | `SELECT … FOR UPDATE` строки-синглтона; второй запрос ждёт и получает `409 setup_already_completed` |
| 5 | Повторное использование невозможно | Флаг не сбрасывается через API; токен погашен. Удаление всех пользователей **не** возвращает инсталляцию в состояние «не настроена» |
| 6 | Не полагаться на frontend | Endpoint сам проверяет состояние; frontend-статус — только для UX |
| 7 | Восстановление администратора | Только серверной процедурой: `plummy admin create` / `plummy admin reset-password` с доступом к серверу; событие в audit |
| 8 | Секреты не в логах | Тела запросов setup не логируются; токен и пароль — `SecretStr`; в логи — только факт и результат |

### 4. Системные настройки в API

- `GET /api/v1/system/settings` — Platform Owner, только чтение, секреты заменены на `configured: true|false`.
- `GET|PATCH /api/v1/organizations/current/settings` — Organization Admin; ответ содержит заданные и effective
  значения.

## Alternatives

| Вариант | Почему отклонён |
|---|---|
| Setup разрешён, пока нет пользователей, без токена | Захват свежей инсталляции первым пришедшим; повторное открытие setup после удаления пользователей |
| Токен выводится в логи при старте | Нарушает запрет секретов в логах; логи часто уходят во внешние системы |
| Только CLI-setup | Безопасно, но хуже quick start (§5 setup wizard). Оставлен как режим `cli_only` |
| Instance Settings редактируются Platform Owner через API | Компрометация одной web-учётной записи позволяет открыть доступ во внутреннюю сеть (ADR-007) и ослабить лимиты. Возможно в будущем отдельным ADR с дополнительной защитой |
| Универсальная таблица настроек | Нет типизации и валидации, смешение уровней, риск хранения секретов в открытом виде |

## Consequences

- Изменение Instance Settings требует доступа к серверу и перезапуска процессов — осознанный компромисс в пользу
  безопасности.
- Появляются группы API `setup` и `system` (расширение списка §10, утверждённое этим ADR).
- Permission `platform.settings.manage` заменяется на `platform.settings.read`.
- Нужны CLI-команды администрирования (входят в backend-артефакт).

## Security considerations

- Bootstrap token: одноразовый, ограничен по времени, хранится в БД только в виде хэша; rate limit на `initialize`;
  проверка `Origin` (сессии и CSRF cookie ещё нет); audit `setup.completed` и `setup.initialize.rejected`.
- Контрольные сценарии **SC-03**, **SC-04** — [SECURITY_MODEL.md §18](../SECURITY_MODEL.md).
