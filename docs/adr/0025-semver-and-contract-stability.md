# ADR-025: SemVer and Contract Stability from 1.0.0

- **Status:** Accepted
- **Date:** 2026-11-28
- **Amends:** [ADR-009](0009-automatic-versioning.md) (релизы, patch-релизы, CHANGELOG)

## Context

Выход Фазы 13 — релиз 1.0.0: «стабильные contracts и production readiness» (PROJECT_BLUEPRINT §19). До 1.0.0
контракт API официально не стабилен ([API_CONTRACTS.md §1.1](../API_CONTRACTS.md)), между релизами 0.x менялись
переменные окружения, секреты production-стека и роли БД (`split-db-roles.sh` в 0.5.0).

Инсталляцию разворачивает и обновляет администратор организации ([ADR-012](0012-single-organization-deployment.md)).
Он должен заранее знать, что при обновлении может сломаться: интеграции с API, скрипты вокруг CLI, файлы окружения
и секретов, backup. ADR-009 описывает только номер версии, но не то, что номер обещает. Нет CHANGELOG, страниц
GitHub Release и правила для patch-релизов: hook ADR-009 после релиза `X.Y.Z` переводит ветку на
`X.(Y+1).0-dev.1`, что не подходит для исправления выпущенной версии.

## Decision

### 1. Публичный контракт

С 1.0.0 номер версии следует [SemVer 2.0.0](https://semver.org/) относительно **публичного контракта**:

| Часть | Что входит |
|---|---|
| REST API | Пути под `/api/v1`, методы, параметры запроса, поля запросов и ответов, коды ошибок (`code`) и HTTP-статусы, права (`permission`) маршрутов, заголовки `X-CSRF-Token`, `Idempotency-Key`, `Retry-After` ([API_CONTRACTS.md](../API_CONTRACTS.md)) |
| SSE | Имена событий `POST /chat/stream`, их поля и порядок ([API_CONTRACTS.md §3](../API_CONTRACTS.md)) |
| Журнал аудита | Имена событий (`action`), `outcome`, поля `AuditEvent` — на них строят интеграции с SIEM |
| CLI | Команды и флаги `python -m plummy.cli`, коды выхода |
| Конфигурация | Переменные окружения и `*_FILE` ([DEPLOYMENT.md](../DEPLOYMENT.md)), формат `CONFIG_FILE` (Instance Settings), имена файлов секретов production-стека |
| Развёртывание | Сервисы, volumes и профили `compose.prod.yaml`, скрипты `deploy/scripts/` и их аргументы |
| Данные | Формат backup `deploy/scripts/backup.sh` (manifest, дамп, объекты); схема БД меняется только миграциями |

Не входят в контракт и меняются в minor-версиях без отдельного предупреждения: внутренние Python-интерфейсы
(ports, use cases, адаптеры), схема БД как таковая, тексты сообщений об ошибках (`message`, в отличие от `code`),
формат логов, frontend и его маршруты, dev-окружение `compose.yaml`, `compose.e2e.yaml`, тестовые фейковые сервисы.
Пункты спецификаций с пометкой **[Proposed]** не входят в контракт, пока не реализованы.

### 2. Что считается ломающим изменением

Ломающее (только в major): удаление или переименование пути, поля, параметра, события, команды, переменной; новое
обязательное поле запроса или параметр без значения по умолчанию; смена типа или смысла поля; новое право на
существующем маршруте; смена кода ошибки или HTTP-статуса для того же случая; изменение формата backup, при котором
новая версия не восстанавливает прежний backup; шаг обновления, требующий ручного действия администратора.

Не ломающее (minor): новые маршруты, необязательные поля запросов, поля ответов (клиенты игнорируют неизвестные
поля, API_CONTRACTS §1.1), новые события SSE и аудита, новые значения перечислений в ответах, новые переменные с
безопасным значением по умолчанию. Patch — только исправления без изменения контракта.

Исключение — безопасность: если уязвимость нельзя закрыть без изменения контракта (например, нового права на
маршруте), изменение выходит в minor или patch и описывается в CHANGELOG в разделе `Security` с указанием, что
затронуто.

### 3. Deprecation

Устаревающая часть контракта сначала помечается и работает до следующего major: в OpenAPI — `deprecated: true`, в
документации — пометка с версией и заменой, в CHANGELOG — раздел `Deprecated`. Устаревшая переменная окружения
продолжает читаться и даёт предупреждение в логе при старте. Удаление — только в major и только после пометки хотя бы
в одном minor-релизе.

### 4. Обновление и поддержка

- Внутри 1.x поддерживается обновление с любого 1.x на более поздний 1.x без ручных шагов: `migrate` применяет
  миграции, сервисы стартуют. CI проверяет обновление с предыдущего релиза (upgrade path, ADR-023 §6).
- Обновление 0.5.0 → 1.0.0 поддерживается и проверяется в CI; с версий до 0.5.0 — через 0.5.0
  (`split-db-roles.sh`).
- Downgrade не поддерживается: откат — восстановление backup, сделанного до обновления.
- Backup, сделанный версией 1.x, восстанавливается той же или более поздней 1.x.
- Исправления безопасности выходят для последнего minor. Patch-релиз `X.Y.(Z+1)` делается из ветки `release/X.Y`,
  созданной от тега `vX.Y.Z`: `scripts/version.py set X.Y.(Z+1)-dev.1`, исправление, `scripts/version.py release`;
  исправление переносится и в `main`.

### 5. CHANGELOG и релизы

- `CHANGELOG.md` в корне в формате [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/): раздел
  `Unreleased` и разделы релизов с датой; группы `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.
- Коммит, меняющий поведение для администратора, пользователя или интегратора, дополняет `Unreleased`. Ломающее
  изменение или ручной шаг обновления описывается отдельно, с инструкцией.
- `scripts/version.py release` переносит `Unreleased` в раздел версии с датой и отказывает, если `Unreleased` пуст.
- Пуш тега `vX.Y.Z` создаёт GitHub Release (workflow), текст — раздел версии из CHANGELOG; версии `0.y.z` —
  обычные релизы, `X.Y.Z-dev.N` тегов не получают.

### 6. Проверка контракта в CI

OpenAPI-схема API хранится в репозитории как snapshot. Тест сравнивает схему приложения со snapshot: любое
изменение требует обновить snapshot в том же коммите, а удаление пути, поля или параметра без пометки deprecated
отклоняется. Так изменение контракта видно в diff и в ревью.

## Alternatives

| Вариант | Почему не выбран |
|---|---|
| Стабилен только REST API | Администратор ломается и на переменных, CLI и backup; эти части тоже интеграционные поверхности |
| Новая версия префикса (`/api/v2`) на каждое ломающее изменение | Две версии API в одной инсталляции удваивают тесты и проверки прав; major-релиз проще и честнее |
| Calendar versioning | Не согласуется с ADR-009 и вехами roadmap; не говорит, есть ли ломающие изменения |
| Поддержка нескольких minor | Для self-hosted проекта с одним сопровождающим нереалистично; обновление внутри 1.x без ручных шагов делает переход на последний minor дешёвым |
| CHANGELOG генерируется из сообщений коммитов | Коммиты пишутся для разработчиков; администратору нужны изменения поведения и шаги обновления |

## Consequences

- Изменение API требует обновить snapshot OpenAPI, документацию и `Unreleased` в одном коммите.
- Часть пунктов [Proposed] до 1.0.0 придётся принять, убрать или явно вынести за контракт (шаг 13.1).
- Внутренние интерфейсы провайдеров и коннекторов не обещаются стабильными: руководства для разработчиков (шаг 13.5)
  описывают расширение в рамках репозитория, а не отдельные плагины.
- Образы в реестр не публикуются: администратор собирает их из тега (`docker compose build`). Публикация образов —
  отдельное решение.

## Security considerations

Исключение для безопасности (§2) не позволяет держать уязвимость открытой ради совместимости. Раздел `Security`
CHANGELOG и SECURITY.md сообщают, какие версии получают исправления. Workflow релиза использует только токен
репозитория с правом на релизы и не имеет доступа к секретам инсталляций.
