# ADR-005: Assistant Access Model

- **Status:** Accepted
- **Date:** 2026-11-17
- **Amended by:** [ADR-012](0012-single-organization-deployment.md) — одна организация на инсталляцию; Org Admin →
  Administrator; основа доступа на уровне KB — ADR-012 п.7 (вместо ADR-004).

## Context

По продуктовой модели Member работает только с **разрешёнными** ассистентами (blueprint §2). Модель данных blueprint
(§9) не содержит отдельной сущности доступа к ассистентам: есть `Assistant`, `AssistantKnowledgeBase` и
`KnowledgeBaseAccess`. Доступ к документам в MVP определяется на уровне Knowledge Base (ADR-012). Требуется правило,
которое однозначно отвечает «может ли пользователь использовать ассистента» и не допускает попадания недоступных
документов в контекст LLM.

## Decision

Доступ к ассистенту в MVP **наследуется от Knowledge Bases**, подключённых к ассистенту.

1. Ассистент связан с одной или несколькими KB (`assistant_knowledge_bases`).
2. Пользователь может использовать ассистента, только если у него есть доступ уровня не ниже `read` **ко всем** KB,
   подключённым к ассистенту (прямой, через группу или через `knowledge_bases.manage`).
3. Нет доступа хотя бы к одной подключённой KB → ассистент пользователю **недоступен** целиком (не «частично»).
4. Ассистент, не связанный ни с одной KB, обычным пользователям недоступен. Его могут использовать только
   пользователи с `assistants.manage` — для настройки и предпросмотра. Публичного режима в MVP нет.
5. Ассистент со статусом `disabled` недоступен для чата никому.
6. Доступность вычисляется backend **при каждом запросе** (список, карточка, создание диалога, каждое сообщение
   чата, открытие цитаты), а не только при отображении списка.
7. Изменение доступа к KB (выдача/отзыв, изменение состава группы, удаление KB или пользователя из группы)
   автоматически меняет доступность связанных ассистентов; отдельного состояния доступа к ассистенту нет.
8. Retrieval использует источники, которые backend вычисляет сам: источники KB ассистента ∩ источники KB, доступных
   пользователю. Идентификаторы KB или источников от frontend **не принимаются** в chat API и не используются для
   авторизации.
9. Недоступные документы исключаются в SQL-запросе retrieval до передачи контекста LLM (ADR-012).

## Alternatives

| Вариант | Почему не выбран для MVP |
|---|---|
| Отдельная таблица `assistant_access` (пользователи/группы) | Второй, независимый от KB список доступа: легко выдать ассистента пользователю без доступа к его KB и получить утечку или «пустые» ответы. Отложено. |
| Частичный доступ: ассистент доступен, retrieval только по доступным KB | Ответы одного ассистента отличаются у разных пользователей непредсказуемо; пользователь не понимает, почему ответ неполный; сложнее тестировать. Отложено. |
| Доступ к ассистенту для всех пользователей инсталляции | Нарушает least privilege (§1) и требование «разрешённые ассистенты» (§2). |

## Consequences

- Таблица доступа к ассистентам не создаётся. Права на ассистента выводятся из `knowledge_base_access`, групп и ролей.
- Администратор, подключая к ассистенту новую KB, может сделать ассистента недоступным части пользователей. UI
  показывает, сколько пользователей потеряют доступ, до сохранения **[Proposed]**.
- Удаление KB отвязывает её от ассистентов; ассистент без KB становится недоступен обычным пользователям.
- Диалоги остаются у владельца: историю можно читать, но новое сообщение в диалоге с недоступным ассистентом
  отклоняется; открытие цитат проверяет доступ к документу заново.
- Administrator и Knowledge Manager (имеют `knowledge_bases.manage`) получают доступ ко всем ассистентам,
  к которым привязана хотя бы одна KB.

## Security considerations

- Проверка выполняется в use case (`PermissionPolicy.can_use_assistant`) и повторяется на каждом сообщении.
- Retrieval дополнительно пересекает источники с доступными пользователю KB (defense in depth), даже если правило п.2
  уже выполнено.
- Ответы API не раскрывают существование недоступного ассистента (`404`), кроме случая собственного диалога
  пользователя (`403 assistant_unavailable`).
- Контрольный сценарий **SC-01** — [SECURITY_MODEL.md §18](../SECURITY_MODEL.md).

## Implementation notes

- Вычисление доступности — один SQL-запрос: нет ни одной KB ассистента, для которой отсутствует эффективный доступ
  пользователя. Кэш допустим только в пределах запроса.
- `GET /assistants` возвращает доступные для чата ассистенты; для `assistants.manage` — все ассистенты с полем
  `availability` (причина недоступности для текущего пользователя).
- Будущее (не MVP): персональные разрешения на ассистентов; доступ через группы; публичные ассистенты для всех
  пользователей; частичный доступ к KB одного ассистента. Каждое — отдельным ADR, superseding или расширяющим этот.
