# ADR-015: User Onboarding by Activation Link

- **Status:** Accepted
- **Date:** 2026-11-18

## Context

Автоматической регистрации нет (§5 blueprint): пользователей создаёт Administrator. Черновик
[API_CONTRACTS.md §2.4](../API_CONTRACTS.md) предлагал временный пароль со сменой при первом входе. Тогда
администратор знает пароль пользователя и передаёт его по стороннему каналу, а система должна поддерживать
«ограниченную» сессию до смены пароля. Email-инфраструктуры в MVP нет, поэтому приглашение письмом невозможно.
В схеме уже есть статус пользователя `invited`.

## Decision

1. `POST /api/v1/users` создаёт пользователя в статусе `invited` **без пароля** и один раз возвращает ссылку
   активации `{PUBLIC_URL}/activate#token=<token>`. Администратор передаёт ссылку пользователю сам.
2. **Токен:** 256 бит (`secrets.token_urlsafe(32)`), срок действия 72 ч. В БД — только SHA-256
   (`user_activation_tokens`, одна строка на пользователя). Токен не логируется и больше никогда не показывается.
   Токен находится во фрагменте URL (`#…`): браузер не отправляет фрагмент на сервер и в `Referer`, поэтому он не
   попадает в логи прокси.
3. **Активация** — публичный `POST /api/v1/auth/activate { token, password }`. Пароль проверяется политикой
   ADR-013 §3. В одной транзакции с блокировкой строки пользователя: пароль, статус `active`,
   `password_changed_at`, удаление токена, audit `user.activated`, новая сессия (как login). Ответ — DTO `Session`.
4. **Ошибки:** неверный, истёкший, использованный токен, а также пользователь, который уже не `invited` (отключён,
   удалён, активирован) → одинаковый `400 activation_token_invalid`. Отказы пишутся в audit
   (`user.activation.rejected`). Лимит — 10 попыток в минуту на IP (Redis, fail closed).
5. **Перевыпуск:** `POST /api/v1/users/{id}/activation` (`users.manage`) — только для `invited`; прежний токен
   перестаёт действовать. Отключение или удаление пользователя делает токен бесполезным.
6. Вход пользователя `invited` невозможен (пароля нет) — тот же `401 invalid_credentials`.

## Alternatives

| Вариант | Почему отклонён |
|---|---|
| Временный пароль + обязательная смена (черновик) | Администратор знает пароль; пароль передаётся вне системы; нужна «ограниченная» сессия и проверка флага на каждом запросе |
| Пароль задаёт администратор навсегда | Нарушает принцип: пароль знает только пользователь |
| Приглашение по email | Нет email-инфраструктуры в MVP; появится вместе с password reset |
| Токен в query-строке | Попадает в логи прокси, историю и `Referer` |

## Consequences

- Новая таблица `user_activation_tokens`, новый публичный endpoint с rate limit, frontend-страница `/activate`.
- Срок 72 ч — константа; при необходимости станет Instance Setting.
- Когда появится email-инфраструктура, ссылка будет отправляться письмом тем же механизмом.

## Security considerations

- Компрометация БД не раскрывает действующие токены (только SHA-256 256-битных значений).
- Перехват ссылки до активации даёт доступ к учётной записи — как и перехват временного пароля; срок 72 ч и
  перевыпуск ограничивают окно. Администратор видит, что пользователь активирован (статус).
- Одинаковая ошибка для всех причин отказа не позволяет перебором узнавать состояние учётных записей.

## Implementation notes

`application/users/` — создание пользователя и перевыпуск ссылки; `application/auth/activation.py` — активация;
`infrastructure/db` — `SqlActivationTokenRepository`.
